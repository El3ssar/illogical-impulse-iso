# Illogical Impulse ISO — Configuration & Tweaking Guide

How to make this distro *yours*: identity, branding, packages, dotfiles,
shells, plugins. This guide never touches build internals — for how the
pipeline itself works (scripts, recipes, scaffolding), read
[BLUEPRINT.md](BLUEPRINT.md).

Everything below follows one rule: **edit declarative inputs, then
`just build`**. Nothing is patched by hand inside images.

---

## 1. The mental model

Three dials control the distro:

| Dial | Lives in | Controls |
|---|---|---|
| **Identity** | `distro.toml` + `overlay/assets/` | name, version scheme, branding art |
| **Payload** | `packages/*.list` | what software ships |
| **Experience** | `overlay/skel-distro/` (+ `overlay/airootfs/`) | how it feels: dotfiles, defaults, system config |

And one layering principle — the **skel layer cake**, merged at build time
(later layers win):

```
upstream dots  →  overlay/skel-distro  →  profiles/<name>/skel
(end-4's rice)    (the distro's taste)     (your personal taste)
```

`just build` produces the public distro (first two layers).
`just build <profile>` adds the personal layer. Upstream stays pristine —
it's a read-only submodule; your overrides survive every `just update`.

## 2. Identity & branding

### Names, URLs, versioning — `distro.toml`

Every identity string lives there and ONLY there: `id`, `name`,
`pretty_name`, `publisher`, URLs, ANSI color, ISO name/label prefixes.
Change a value, rebuild — os-release, the ISO filename/volume label,
profiledef, and the release stamp all follow. Never hardcode the name in a
script or config; if you find one, it's a bug.

### Visual brand — `overlay/assets/branding/`

| File | Source of | Regenerated by |
|---|---|---|
| `logo.svg` | distro icon: Calamares logo, `/usr/share/pixmaps` (os-release `LOGO=`), fastfetch | `just assets` |
| `icon-source-256.png` | raster original the SVG was traced from (reference only) | — |
| `wordmark.svg` | Calamares welcome hero (`welcome.png`) | `just assets` |
| `../default-wallpaper.png` | live + installed default wallpaper, welcome hero background | `just assets` |

Workflow: replace the source file → `just assets` → review the diff →
commit the regenerated PNGs. The pipeline never calls gen-assets itself;
generated art is reviewed, versioned output.

### Calamares look — `overlay/calamares/branding/illogical-impulse/`

- `branding.desc` — strings shown in the installer + sidebar/background
  colors. Keep `welcomeStyleCalamares: true` (historic bug if false).
- `stylesheet.qss` — Qt CSS for buttons/widgets.
- `slideshow.qml` + `slides/*.png` — the install-time slideshow. Drop in
  new 16:9 PNGs and list them in the QML.

### Boot menu & console identity

- Boot entries/titles: `overlay/efiboot/loader/entries/*.conf`.
- TTY banner & post-login message: `overlay/airootfs/etc/issue`, `etc/motd`.
- fastfetch: `overlay/airootfs/etc/fastfetch/config.jsonc` renders the
  distro icon via terminal graphics (kitty protocol; chafa ASCII on TTYs).
  The classic ASCII-art logo stays at `etc/illogical-impulse/logo.txt`.

## 3. Packages

Four manifests under `packages/` (one package per line, `#` comments):

| File | Meaning |
|---|---|
| `base.list` | infrastructure present on live ISO **and** installed system (greetd, polkit, zram…) |
| `installer.list` | live/installer-only — purged from the target by `ii-post-install` |
| `goodies.list` | **the batteries** — every app the distro ships (browser, office, dev tools…) |
| `nvidia.list` | never baked; hardware-detected at install (see below) |

Plus `profiles/<name>/packages.list` for personal builds.

Things to know:

- **Official vs AUR is automatic.** Each name is checked against the sync
  db at prepare time; unknown names are assumed AUR and routed through
  `just prebuild` (built once, cached in `/var/cache/ii-extra-repo`,
  version-checked against the AUR on every build).
- **Broken AUR package?** Drop a fixed PKGBUILD at
  `overlay/aur-pkgbuilds/<pkgname>/PKGBUILD` — local overrides always win
  over the AUR (this saved us twice already: `otf-space-grotesk`,
  `qt6-avif-image-plugin`).
- **Upstream rice dependencies are never listed manually** — they're
  scraped from the dots' own PKGBUILDs each build and stay in sync with
  `just update`.
- **NVIDIA**: edit `packages/nvidia.list` only to change driver variants.
  At install, `ii-post-install` reads `/sys/bus/pci` and installs the open
  driver (Turing+), the 580xx legacy (Maxwell/Pascal/Volta), or nothing —
  offline, no questions.

## 4. Dotfile overrides

### Distro-wide: `overlay/skel-distro/<path-under-$HOME>`

Anything here lands in `/etc/skel` *on top of* the upstream dots, for every
installed user. Examples:

```
overlay/skel-distro/.config/nvim/init.lua          # distro nvim config
overlay/skel-distro/.config/kitty/kitty.conf       # override upstream's kitty.conf
overlay/skel-distro/.zshrc                          # distro zsh setup
overlay/skel-distro/.local/state/quickshell/...    # OOB state (kitty-theme fallback lives here)
```

Rules of thumb:

- Mirror the exact path upstream uses to *replace* a file; new paths just
  add files.
- Executables: shebang'd files get +x restored automatically in the image
  (mkarchiso strips it — known bug, handled).
- Don't pre-generate color-scheme/state files beyond the shipped
  kitty-theme fallback — first-boot color generation owns those.
- The live user does **not** see skel-distro (it gets pristine upstream +
  `overlay/skel-live/`) — so "try" sessions showcase stock II, installs get
  the distro flavor. Put live-only things (installer icon, live keybinds)
  in `skel-live/`.

### Personal: `profiles/<you>/skel/` + `fetch.list`

Same mechanics, merged last, only in `just build <you>`. For configs that
live in their own git repos (your nvim config, antidote), don't vendor —
pin them in `profiles/<you>/fetch.list`:

```
.config/nvim     git@github.com:You/nvim-config.git   <commit-sha>
.fizsh/.antidote https://github.com/mattmc3/antidote  <commit-sha>
```

Cloned at build time (cached in `.fetch-cache/`), `.git` stripped, merged
into the skel. Bump the sha to update.

> Want a pinned repo distro-wide instead of per-profile? That needs a small
> pipeline extension (a distro-level fetch.list) — see BLUEPRINT.md §"easy
> extensions".

### System files (not under $HOME)

`overlay/airootfs/<absolute-path>` — greetd config, systemd drop-ins,
sudoers, sysctl, udev rules, anything. Copied verbatim into the image.

## 5. Recipe: shipping a different default shell (fizsh example)

Four moves, all declarative:

1. **Package** — add `fizsh-git` to `packages/goodies.list`.
2. **Login shell** — in `overlay/calamares/modules/users.conf` set:
   ```yaml
   userShell: /usr/bin/fizsh
   ```
   (Check the binary path the package actually installs.)
3. **Config** — ship `.fizshrc` / `.zshrc` / plugin list in
   `overlay/skel-distro/` (see §6 for antidote).
4. **The gotcha** — upstream's terminal configs launch **fish** explicitly
   (e.g. `shell fish` in kitty.conf), which overrides the login shell
   inside terminals. Override that file in `skel-distro` too (e.g. a
   kitty.conf with `shell .` to use the login shell) or your default shell
   will exist but never be seen.

Then `just build`, `just vm --disk`, and check both a terminal and a TTY
login land in the right shell.

## 6. Zsh plugins with antidote

Antidote is a plugin *manager* — at runtime it reads a plain-text plugin
list and clones/loads them. For a distro, runtime cloning means first-start
network delays, so pin antidote itself and let the plugin list be the only
moving part:

1. Pin antidote via `fetch.list` (profile today; distro-level once the
   extension lands): `.fizsh/.antidote https://github.com/mattmc3/antidote <sha>`
2. Ship the plugin list — `overlay/skel-distro/.zsh_plugins.txt`:
   ```
   zsh-users/zsh-autosuggestions
   zsh-users/zsh-syntax-highlighting kind:defer
   zsh-users/zsh-history-substring-search
   ```
3. Load it from your shipped `.zshrc`/`.fizshrc`:
   ```zsh
   source ~/.fizsh/.antidote/antidote.zsh
   antidote load ~/.zsh_plugins.txt
   ```

First shell start clones the plugins (needs network once, then cached in
the user's home). To make even that offline, vendor each plugin via
fetch.list and `antidote load` a static bundle instead.

## 7. Plugins for everything else — the general pattern

One principle: **no first-boot network dependencies for core UX; pin
versions for everything vendored.**

| Tool | Pattern |
|---|---|
| **neovim** | Ship the config via skel (distro or profile). Lazy.nvim will bootstrap plugins over the network on first launch — acceptable for a dev tool. To make it instant/offline, vendor the plugin directory via `fetch.list` pointing at your locked config repo. |
| **yazi** | Flavors/plugins are plain directories — vendor them under `skel-distro/.config/yazi/{flavors,plugins}/` (strip any nested `.git`). |
| **zellij / tmux** | Config + layout files in skel; zellij plugins are `.wasm` files you can ship directly. |
| **bat / eza / starship** | Pure config files — skel them. |
| **VS Code / Cursor extensions** | Don't bake (per-user state, licensing); document or script via the future welcome app. |

## 8. Building & testing your changes

```sh
just build              # public distro → out/*.iso
just build <profile>     # + personal profile layer
just validate           # ~55 static checks on the assembled profile (no root)
just vm                 # boot the ISO in QEMU
just vm --disk          # + attach a 40G test disk → run a full install
just vm --installed     # boot the installed test system (no ISO)
just vm --fresh-disk    # wipe the test disk for a clean install run
just preview [app]      # live-preview a standalone Quickshell app (no build)
just update             # bump the dots submodule (--check = policy dry-run)
```

Iteration costs: package-list or skel changes need a full `just build`
(~20–40 min, AUR cache warm). Pure Calamares/branding config changes too —
everything rides inside the squashfs. **But you rarely need a full build to
test a change:** `just preview <app>` opens a standalone Quickshell app
(welcome card, Control Center, app-dashboard, widgets) live from the source
tree and hot-reloads on save — no build, no install. CLI/script behaviour
(iictl, ledger, packs) is tested in a throwaway container (`just nspawn`,
planned). Reserve the full `just build` + `just vm` boot for changes that
actually touch the session, install flow, bootloader, or package set.

## 9. On the installed system: iictl

The distro CLI ships on every install (`/usr/local/bin/iictl`):
`update` (dots via upstream's own setup), `update --system` (paru: repos +
AUR + dots), `doctor` (venv/greetd/boot/pacman health), `venv` (rebuild the
Quickshell python env), `welcome` (reopen the distro welcome card),
`version`. The welcome card auto-shows once, on the login after upstream's
own welcome app — sequencing markers live in `~/.local/state`.

## 10. When something breaks

```
Live session:        /var/log/greetd-boot.log, /var/log/ii-session.log
During install:      /var/log/ii-stage… → see Calamares dialog; ERR traps print file:line
Installed target:    /var/log/ii-post-install.log, ii-verify.log,
                     ii-prepare-bootloader.log, ii-finish-systemd-boot.log
Build chroot:        /var/tmp/ii-iso-work/…/airootfs/var/log/customize_airootfs.log
                     (workdir is kept on failure)
```

Full failure-mode encyclopedia: [CLAUDE.md](../CLAUDE.md) §"Historic bugs".
